《盗贼之海》的海面：
FFT 巨浪、船体浮力与多人一致性

《盗贼之海》（Sea of Thieves）是英国 Rare 工作室基于 Unreal Engine 4 开发的共享世界多人海盗游戏，2018 年 3 月由 Xbox Game Studios 发行。它的海面以风格化的高耸长浪著称：风暴中船被巨浪整体抬起又滑下，同船与敌对船队的玩家看到的是同一片浪。

本报告依据 Rare 在 SIGGRAPH 2018 发表的讲座论文《The Technical Art of Sea of Thieves》、GDC 2019 讲座讲稿、官方开发日志报道，以及 Tessendorf 的海洋模拟原始讲义、《Atlas》等游戏的 GDC 与 SIGGRAPH 讲稿、引擎文档，以及中、日、韩文的技术分享，还原三件事：巨浪如何由 FFT 频谱合成并按海况放大，船体如何通过浮力探针随浪运动，多人游戏如何让每个客户端看到一致的海浪与船。Rare 未公开的部分均标注为推断并给出依据。

巨浪从哪里来

FFT 频谱 + 三档海况海面是 Tessendorf FFT 海洋。浪高随风速平方增长，风暴档位放大频谱与 choppiness，浪尖次表面色与泡沫强化视觉高度。

怎样保证各端一致

共享时钟，服务器权威海面是“种子、参数、时间”的纯函数，各端独立求值，只同步时钟与海况；船由服务器模拟并复制，甲板玩家用相对船体的坐标。

UE5 与手游

可复现，手游需三档降级UE5 需自写 GPU FFT 级联、CPU 玩法波段与网络时钟；手游按 FFT、烘焙循环序列、顶点 Gerstner 分档，同步结构不变。

现象拆解与资料边界

玩家看到了什么，Rare 公开了什么，哪些只能推断

《盗贼之海》（Sea of Thieves）由英国工作室 Rare 开发、Xbox Game Studios 发行，2018 年 3 月登陆 Xbox One 与 Windows，基于 Unreal Engine 4。它是一款共享世界的多人海盗冒险游戏：同一服务器上有多支玩家船队，每支船队 1 到 4 人共同操作一艘帆船，航行、交战、寻宝。海洋既是场景也是玩法本身，浪的高低直接决定航行难度、炮击命中和登船时机。

这些现象可以拆成三个技术问题：

  1. 巨浪隆起：风暴区里海面出现高耸、陡峭的长浪，船被整体抬起，再沿浪背滑下；平静海域则只有低矮的起伏。浪的高度随位置和天气变化，而且画面风格化，浪尖透出明亮的青绿色。
  2. 船体随浪运动：船的升沉（heave）、纵摇（pitch）、横摇（roll）与脚下的浪形吻合，没有明显的穿插或悬空；甲板上会积水，水从舱板缝隙渗到下层。
  3. 多人一致性：同船的四名玩家、隔海对射的两支船队，看到的浪峰位置、船的姿态必须一致，否则炮弹会打进一个只在某个客户端存在的浪里，登船的玩家会落在对方看不到的位置。

资料边界

Rare 公开的海洋技术资料很少。唯一有技术细节的一手资料是 SIGGRAPH 2018 的讲座论文《The Technical Art of Sea of Thieves》一手[1]，它覆盖海面的模拟方法、着色、泡沫与甲板积水，但没有涉及浮力、物理与网络。网络方面能找到的一手材料是 Rare 在 GDC 2019 自动化测试讲座里对服务器、客户端架构的描述 [2]，以及 2016 年开发日志中“海浪在所有玩家之间同步”的表述 [3]。中文、日文、韩文资料中只找到讲座视频的转载与综述性的归纳 [4][5]，没有超出 Rare 原文的细节。

海面：FFT 海洋与巨浪隆起

Tessendorf 频谱合成、海况分档与风格化着色

2.1 Rare 确认的部分

论文第一句即说明底层海面模拟是 Tessendorf 2001 年 FFT 方法的一个实现一手[1]。Rare 在 2016 年的开发日志中补充了思路：先建立接近真实的物理基础，再由美术在其上叠加风格化，使海面“看起来风格化，但行为仍然像水” [3]。论文给出的其他细节如下：

  • 颜色：在深水色（deep water colour）与次表面色（sub-surface water colour）之间插值，权重由视角、太阳方向和浪峰遮罩（wave peak mask）共同决定。
  • 浪峰遮罩：取自 FFT 的水平位移（choppiness）顶点偏移量。偏移越大越接近浪峰，光在浪峰中穿过的水层更薄，因此显示更多次表面色。这就是浪尖透出青绿色的来源。
  • 泡沫：浪峰泡沫按 Tessendorf 论文的方法生成；物体与水面相交处的泡沫，在以相机为中心的窗口内用深度缓冲比较得到；泡沫缓冲带反馈逐帧模糊，模拟消散；最后与美术手绘的泡沫贴图混合。
  • 海况：水面分平静（calm）、普通（normal）、风暴（stormy）三档，泡沫的生成、扩散与贴图混合随档位变化；平静海面只在物体周围产生泡沫。
  • 其他：面光源高光采用 Karis 的球面最近点近似 [6]，用来表现低角度的大太阳倒影；水下看水面时使用斯涅尔窗（Snell's window）。

2.2 FFT 海洋的原理

Tessendorf 方法把海面高度写成大量正弦波的叠加，每个波矢 k 对应一个复振幅。初始振幅 h₀(k) 由随机数乘以海浪频谱的平方根得到；随时间推进时，每个分量只按深水色散关系 ω(k) = √(g|k|) 旋转相位：

h̃(k, t) = h₀(k)·e^{iω(k)t} + h₀*(−k)·e^{−iω(k)t}
h(x, t)  = Σ_k h̃(k, t)·e^{ik·x}            // 一次二维逆 FFT 得到整张高度图
D(x, t)  = Σ_k −i·(k/|k|)·h̃(k, t)·e^{ik·x}  // 水平位移（choppy），乘以系数 λ 后加到顶点上

常用的频谱是 Phillips 谱 P(k) = A·e^{−1/(kL)²}/k⁴·|k̂·ŵ|²，其中 L = V²/g 由风速 V 决定，ŵ 是风向 [7]。这里有三个与本题直接相关的性质：

  1. 海面是时间的纯函数。给定随机种子、频谱参数和时间 t，整张海面完全确定，没有需要积分的状态。这是第 4 章多人同步方案的数学基础。
  2. 浪高对风速极其敏感。对 Phillips 谱积分可得高度方差与 L² 成正比，即有效浪高与 V² 成正比推导；按波数大小统计能量时，谱峰波长约为 2π·√1.5·L ≈ 7.7·V²/g，风速 10 m/s 时约 80 m，20 m/s 时约 310 m。风速翻倍，浪高约变为 4 倍，波长也变为 4 倍。
  3. 海面按图块（patch）周期重复。FFT 的结果是边长 Lpatch 的可平铺图块，比图块更长的波无法表示。风暴的长浪往往超过常规图块尺寸，需要更大的图块或独立的级联（cascade）。

水平位移 λ·D 让顶点向浪峰聚拢，浪峰变尖、浪谷变平，这是 FFT 海面产生“陡峭感”的关键。λ 过大时曲面会自交，对应雅可比行列式 J 小于 0，Tessendorf 建议用 J 低于阈值的区域生成泡沫 [7]。Rare 所说“按参考论文的方法在浪峰生成泡沫”与这一判据一致，论文原文没有写出 Jacobian 一词推断。

2.3 巨浪隆起是怎样做出来的

Rare 没有公开风暴浪高的参数与实现。结合论文的三档海况、开发日志与风暴的玩法设定，可以把这一效果拆成三个层次推断：

  1. 频谱层：风暴档位对应更高的风速、更大的振幅系数和更大的 choppiness λ。由上面的推导，风速提高 40% 即可让浪高翻倍，所以只需切换少数参数就能得到量级不同的海面。频谱参数需要在档位之间平滑插值，否则海面会突变。
  2. 空间层：游戏里的风暴是一片有边界的区域，社区维基记录它沿固定的循环路径环绕地图移动，一圈约 250 个游戏日（现实约 4 天 4 小时），且所有服务器的风暴位置相同二手[8]。单张 FFT 图块无法在空间上改变海况，常见做法是同时计算平静与风暴两组频谱（或两组级联），按与风暴中心的距离生成权重场，在顶点着色器和物理查询中按权重混合两组位移。
  3. 风格层：浪尖次表面色、泡沫和美术贴图让同样的高度场显得更“夸张”。浪峰遮罩越大颜色越亮，视觉上强化了浪峰的高度与透光感 [1]。

这一推断与 Rare 的表述相符：开发日志把风暴描述为世界中一个“巨大的、物理的东西”，浪变大后掌舵更难，浪会拍上甲板，水会渗过木板滴到下层二手[9]。其中甲板积水不是海面 FFT 的一部分，论文说明它使用基于 Mei 等人方法的 GPU 浅水模拟 [1][10]。

船体随浪：浮力探针与高度查询

从海面函数到刚体受力，以及物理用的海面从哪里来

3.1 已知事实

Rare 没有公开浮力与船体物理的实现。能确定的旁证有两条。其一，Masella 在 GDC 2019 讲座中说明，测试“玩家转动舵轮”时场景里只放玩家、一个供站立的平台和舵轮，不加载船，因为船是一个“昂贵的对象”；舵轮对船舵（rudder）的影响另行测试一手[2]。这说明操舵输入与船体运动在代码上是解耦的组件。其二，GamersNexus 的平台对比评测认为，开发者特意同步海浪，是因为浪在机制上会影响船的位置二手[11]。

3.2 浮力探针模型

游戏里最常用的做法是在船体上布置若干浮力探针（buoyancy probe，也称 pontoon）。每帧对每个探针查询其水平位置处的海面高度，按淹没深度施加向上的力，并在探针处施加与速度相反的阻尼力。力施加在探针的世界位置上，因此除了合力产生升沉，还会产生力矩，带动纵摇和横摇：

for each probe p:
    d   = H(p.xy, t) − p.z                        // 淹没深度；H 为海面高度查询
    if d > 0:
        F = k·min(d, dmax) − c·v_z(p)            // 弹簧项近似静水浮力，阻尼项近似辐射阻尼与粘性
        body.AddForceAtLocation(F·up, p)
body.AddForce(−m·g·up)

探针数量决定船能表现出的运动自由度：一个探针只能升沉；沿龙骨排两个以上才有纵摇；左右舷都布置才有横摇。探针越多，船对短波越“迟钝”，因为短于船长的波在多个探针上相互抵消，这恰好符合真实船舶对短波不敏感的特性。下方示意中可以切换探针数量观察这一点。

更精确的做法是把船体网格的三角形与水面求交，对淹没部分积分静水压力，再加上压力阻力、黏性阻力和拍击力。Kerner 2015 年的文章是这一方法在游戏中的经典介绍 [12]。它的代价是每帧要对数百个三角形做水面查询和裁剪，适合单机或少量船只；多人游戏里一艘船常常对应数十个玩家视角，开销更敏感。

3.3 FFT 海面的高度查询问题

带水平位移的 FFT 海面不是严格的高度场。网格顶点 x₀ 被移动到 x₀ + λD(x₀)，所以“世界坐标 x 处的海面高度”并不等于 h(x)，而要先求出满足 x₀ + λD(x₀) = x 的 x₀。常见做法是不动点迭代：令 x₀ ← x₀ − (x₀ + λD(x₀) − x)，迭代 3 到 4 次即可收敛。直接按 x 求值的误差随陡度增大，在浪峰附近最明显，船会出现穿插或悬空。示意 1 的“直接按 x 求值”模式可以看到这一误差。

3.4 物理用的海面从哪里来

这是多人海洋游戏最容易被忽略的约束。渲染用的 FFT 通常在 GPU 上以 256² 或更高分辨率逐帧计算，而服务器上的物理需要同样的海面：

  • 专用服务器通常没有 GPU。船的权威物理在服务器上运行，所以物理可用的海面必须能在 CPU 上算出。
  • GPU 回读有延迟。客户端若从 GPU 读回位移图供物理使用，通常要滞后 1 到 3 帧，且与服务器的 CPU 结果不一定逐位一致。

因此合理的结构是把海面分成两部分推断：决定船体运动的低频部分（长涌浪与主浪）在 CPU 上以较低分辨率计算，或者用少量解析波表示，服务器与客户端用同一份代码求值；只影响画面的高频细节（短波、涟漪、法线）只在客户端 GPU 上计算，不参与物理。GamersNexus 引用的游戏设置说明写到“水面细节”选项会同时影响 CPU 与 GPU 性能 [11]，这与 CPU 端也存在海面计算的结构相符，但不能单凭这一点确认。

3.5 站在移动甲板上的玩家

船上的玩家需要随船运动，同时自由行走。UE4 的角色移动组件（CharacterMovementComponent）原生支持基座移动（based movement）：角色站在一个移动物体上时，记录相对该基座的位置，网络复制时也发送相对坐标，客户端再用本地的基座姿态还原世界坐标。只要船本身在各端一致，船上玩家就随之一致。《盗贼之海》是 UE4 项目，采用或扩展这一机制的可能性很高，但 Rare 没有公开说明推断。

04

多人一致性：同一片海，同一条船

共享时钟上的确定性海面、服务器权威的船体与客户端呈现

“不同玩家看到的效果一致”要分三层解决，每层的手段不同：海面靠共享时钟加确定性函数，船靠服务器权威加快照复制，船上的人靠相对基座的坐标。前一层是后一层的前提。

4.1 海面：同步时间与参数，各端自行求值

第 2 章已经说明，FFT 海面是种子、频谱参数和时间的纯函数。只要所有机器使用同一组参数和同一个时钟，就能各自算出同一片海，网络上不需要传输任何海面数据。Rare 的公开材料与这一结构吻合：

  • 2016 年开发日志说明要确保海浪在每个玩家之间同步，让大家看到相同的浪级，海战时尤为重要一手[3]。
  • SIGGRAPH 论文写明，云层只把风向造成的一个偏移向量同步给所有客户端，每个玩家就在相对自己的同一位置看到同样的云一手[1]。这是“只同步少量全局参数，各端本地生成表现”的直接例证。
  • 风暴沿固定循环路径移动，所有服务器的风暴位置相同二手[8]。最自然的实现是把风暴位置写成全局时间的函数，各服务器无需通信即可一致。

其他游戏的一手资料给出了同样的做法。《Atlas》（Grapeshot Games，UE4）的 GDC 2019 讲稿把频谱海面的优点概括为只依赖绝对时间和频谱参数，因而可以在服务器与客户端上独立模拟，在服务器网格之间也能无缝衔接一手[13]；NVIDIA 的博客引述 Grapeshot 的说法，服务器以仅够物理使用的分辨率和 CPU 开销模拟海面，客户端在同一模拟上渲染高质量画面 [14]。《Naval Action》的开发者表示浪会影响横摇、纵摇和弹着点，因此海面以服务器为准，对同场 50 名玩家必须一致 [15]。Unity 的开源海洋插件 Crest 在文档中要求联网游戏让所有客户端共享时间，提供 TimeProviderNetworked，只需设置一个相对服务器的时间偏移 TimeOffsetToServer [16]。

4.2 时钟同步的误差预算

各端时钟的误差 ε 直接变成海面相位误差。深水波的竖直速度上限是 A·ω，所以两端高度差不超过 A·ω·|Δε|。对波长 100 m、振幅 2 m 的涌浪，ω ≈ 0.79 rad/s，50 ms 的时差带来约 8 cm 的高度差；对波长 10 m、振幅 0.3 m 的短波约为 4 cm推导。这一量级在画面上不可察觉，说明海面同步不需要很高精度的时钟，但时钟不能跳变。

UE 自带的 AGameStateBase::GetServerWorldTimeSeconds() 不能直接满足这一点。社区对 UE4 源码的转述显示，客户端在复制回调中直接令偏移量等于“服务器复制来的时间减去本地时间”，没有扣除传输延迟 [17]。结果是客户端时间系统性落后约单程延迟，且每次复制都会整体跳变推断。UE5 Water 插件的 UWaterSubsystem 提供了 SetOverrideSmoothedWorldTimeSeconds 等接口 [18]，Gerstner 波与浮力的查询函数都带显式的时间参数 [19][20]，可以接入自定义的网络时钟。社区讨论也指出，材质端（GPU）与物理端（CPU）的时间来源是分开的，两边都要改 [21]。

推荐的时钟是 NTP 式估计：客户端记录发送时刻 t₀，服务器回传其时间 Tₛ，客户端在 t₁ 收到，偏移估计为 Tₛ + (t₁ − t₀)/2 − t₁；取多次采样中往返时间最短的样本，以有限的速率逐步修正本地时钟，保证时间单调、无跳变。剩余误差来自上下行延迟的不对称，量级为往返时间的几分之一。

时间的浮点精度

服务器可能连续运行数天。单精度浮点在 t 约为 18 到 36 小时之间的最小间隔约 7.8 ms，运行 12 天后达到 0.125 s，海面会出现可见的阶跃。UE5 Water 的相关接口使用 float 时间 [18][19]。对策是在服务器上用双精度累计时间，并在下发前对海面的循环周期取模；Tessendorf 讲义给出了让海面在周期 T 内精确循环的做法，即把每个分量的角频率量化为 2π/T 的整数倍 [7]。

4.3 为什么船必须服务器权威

海面可以由各端独立求值，船却不行。原因是浮点结果在不同硬件之间不能逐位一致：GPU 有融合乘加（FMA），并行归约会改变运算顺序，不同数学库的 sin 实现误差不同 [22]；跨编译器、跨架构的浮点确定性代价很高 [23]。确定性锁步（deterministic lockstep）要求所有机器的模拟逐位相同 [24]，而船受到海浪、碰撞、炮击和多名玩家的输入，微小差异会在几秒内放大成明显的位置偏差。

因此船的状态由服务器模拟并复制给客户端。Rare 的 GDC 2019 讲稿描述的舵轮流程正是这一结构：客户端玩家转动舵轮，舵轮状态通过网络消息发送到服务器，服务器再把新状态复制给其他客户端一手[2]。Rare 社区团队在 2023 年承认，服务器性能下降时玩家会遇到航行中的回拉（rubberbanding）与全局不同步，临时把每台服务器限制为 14 名玩家、5 艘船 [25]；随后的热修复说明中也有针对服务器性能导致不同步的修复 [26]。这些症状与“船和玩家移动以服务器为准，客户端修正本地状态”的架构一致。

服务器物理不必很高频。《Atlas》的讲稿指出服务器模拟常低于 10 Hz，离散的浪高采样在时间上噪声很大，完全依赖力与刚体动力学会增加延迟和不稳定；他们的做法是用船体上的采样点做平面拟合，把拟合平面作为船的目标姿态，再用弹簧滤波逼近浮力效果，目标是在“史诗级”浪高下不让玩家晕船一手[13]。

4.4 客户端怎样呈现船：时间线对齐问题

客户端收到的船体快照总是来自过去。快照插值（snapshot interpolation）的做法是把渲染时间设在“当前时间减去插值延迟”，在两个已收到的快照之间插值。Fiedler 的经验法则是缓冲要能容忍连续丢两个包：30 Hz 发送时约 150 ms，10 Hz 时约 350 ms；用速度做 Hermite 插值可以消除线性插值的抖动 [27]。

海洋游戏在这里有一个特有的问题分析：船按“过去”的时间线呈现，海面却按“现在”的时间求值，两者相差一个插值延迟。100 ms 的延迟足以让船相对本地海面出现几十厘米的穿插或悬空，在浪陡的风暴中更明显。可选的处理方式有三种：

船上的角色以船为基座移动。UE 的角色移动组件用 FSavedMove_Character 缓存本地输入，服务器校验后以 ClientAdjustPosition 纠正，并通过 ReplicatedBasedMovement 让客户端知道角色站在哪个基座上 [28]。站在旋转平台上的客户端会滑动、被纠正而抖动，这是早有记录的问题（UE-58099）[29]。船上玩家的抖动通常由三项叠加而成：船本身的复制误差；角色相对坐标与船体变换不在同一时间戳；基座旋转时相对坐标与世界坐标的转换误差。对策是角色的位置一律以船的局部坐标存储和复制，客户端先插值船，再把角色的局部坐标乘上插值后的船体变换推断。

5.1 网格 LOD

投影网格把屏幕空间的网格投到水平面上，多边形在屏幕上分布均匀、实现简单，《刺客信条 III》与《战舰世界》都在用；缺点是顶点随相机滑动，浪陡时闪烁明显，《战舰世界》为此加了逐像素的牛顿迭代求交来压制抖动 [37]。几何 clipmap 用世界坐标对齐的同心环，顶点吸附在世界网格上，画面稳定，而且每圈的网格密度可以与对应级联的纹理分辨率一一对应；Crest 的 CDClipmaps 用曼哈顿距离做连续 LOD 过渡，相机升高时按 2 的幂缩放整片海面 [33]。对于带水平位移的 FFT 海面与多人场景，clipmap 更合适。

5.2 物理查询的三种方式

  • CPU 上重算同一套波：UE5 Water 的 Gerstner 浮力 [19]、Unity Boat Attack 用 Burst 作业在 CPU 上运行与着色器相同的 Gerstner 公式 [41]。延迟为零，服务器可用；但 FFT 海面需要在 CPU 上再做一次低分辨率 FFT。
  • GPU 结果回读：WaveWorks 提供面向游戏物理的主机回读 [42]，UE4 社区的千船演示测得海面加位移回读约 1 ms [43]；Crest 的 GPU 查询是异步的，需要逐帧轮询直到结果返回 [44]；腾讯 TGDC 2021 介绍的 Aqua 水体方案先记录查询点，由计算着色器批量读出后在下一帧回读，即“延迟一帧”的读取 [45]。这类做法有帧级延迟，专用服务器上不可用。
  • 船周采样高度片：《正当防卫 3》在船体周围等间距采样一次海面，生成一个小高度片，后续所有三角形裁剪与压力计算都在这片高度片上完成 [12]。把昂贵的海面查询次数降到每帧一次网格采样。

06

批判性分析：可以做得更好的地方

以“玩法相关的海面”为中心重新划分职责

前几章还原的结构（FFT 海面、服务器权威的船、共享时钟）在业界是成熟做法。下面几条是本报告认为可以改进或需要明确的地方，均为分析结论分析。

6.1 把海面拆成“玩法波段”和“画面波段”

决定船体运动、炮弹落点和角色落水的只是频谱低频端的长浪与主浪。把这部分定义为玩法波段（gameplay band），要求服务器与所有客户端用同一份代码求值；其余高频分量划为画面波段，只在客户端 GPU 上计算，任何判定都不读取它。这样做有三点好处：

  • 服务器只需在 CPU 上计算一个小尺寸的频谱（例如 64² 的最长级联）或十几个解析波，开销可控，也不依赖 GPU 回读。
  • 客户端的物理预测与服务器使用同一个玩法波段，两端的浮力结果只差浮点误差和时钟误差。
  • 画面波段的振幅有明确上限，例如 0.3 m，它造成的“看到的浪”和“判定用的浪”之间的偏差也就有了上限，可以据此设定命中判定的容差。

《Atlas》的四频段方案与 Crest 为无 GPU 服务器提供的烘焙 CPU 数据 [13][44] 都是这一思路的部分实现，但公开资料里很少把“哪些分量参与判定”作为明确约定写出来。

6.2 浪高与波长解耦，单独控制涌浪

在 Phillips 谱里提高风速会同时拉长波长、加大浪高、延长周期（第 2 章）。美术想要的“更高更陡的浪”并不一定意味着“更长的浪”。《Atlas》改用双 JONSWAP 谱，把本地风浪与大尺度的平滑涌浪分开，并提供振幅覆盖（override amplitude）等参数，以在保持物理合理的同时获得充分的美术控制 [13]。对于追求“夸张巨浪”的风格化游戏，单独的涌浪分量加振幅系数比单纯调风速更直接。陡度需要设上限：雅可比行列式低于 0 的区域会自交，可以在频谱侧限制 choppiness λ，或在网格侧对 J 做钳制。

6.3 风暴用确定性的空间权重场

风暴是局部现象，而 FFT 图块在空间上是均匀的。推荐的做法是同时计算平静与风暴两组频谱（或共享低频级联、只在高频与振幅上区分），由风暴中心、半径和衰减曲线生成权重场，在顶点着色与 CPU 查询中按同一权重混合。风暴中心本身写成全局时间的函数，所有机器无需额外通信即可得到同一权重场。权重场必须是平滑函数，否则边界处的船会受到突变的浮力。

6.4 船的竖直运动交给客户端重建

第 4 章的分析表明，整体快照插值会让船与本地海面错开一个插值延迟。若服务器像《Atlas》那样用平面拟合求目标姿态 [13]，则船的升沉、纵摇、横摇基本是“水平位置、航向、时间”的函数，客户端可以用同一函数在本地重建，只从服务器取水平运动和偶发的冲击偏差。这样既消除了时间线错位，也能减少每次快照需要发送的量。代价是碰撞、炮击、搁浅等冲击需要通过收敛项从服务器状态传给客户端。

6.5 时钟与晕动

UE 默认的服务器时间没有延迟补偿且会跳变（第 4 章），复现时应替换为单调、限速修正的网络时钟，并以双精度累计、按海面周期取模。另外，《Atlas》明确把“巨浪但不让玩家晕船”列为设计目标 [13]。第一人称站在纵摇的甲板上，镜头完全跟随船体会加重晕动感。可以对第一人称镜头的横滚做部分稳定，让地平线的转动幅度小于船体，这是风格化巨浪的必要配套。

07

AI 方法的定位

结论：核心链路不需要神经网络

这一题的核心是“各端得到同一个函数值”，确定性和可复现性比拟合能力更重要。逐项评估如下：

  • 海面合成：FFT 与解析波已经是精确、廉价、可逐帧复现的函数。用神经网络替代只会引入跨硬件的推理差异，违背同步的前提。
  • 船体响应：用小网络从若干浪高采样预测升沉与纵摇在技术上可行，但平面拟合加弹簧的成本已经可以忽略，网络没有收益。
  • 时钟估计：最短往返时间筛选加限速修正已足够，学习型估计器的收益不足以抵消调试成本。

AI 只在离线环节有实际价值：用参考画面或美术示意反推频谱与着色参数的初值，或批量生成泡沫、浪花贴图的变体。这些都不进入运行时，也不影响同步。

性能、带宽与手游

开销估算、网络流量与移动端降级路线

8.1 性能开销

《盗贼之海》的设置说明写到“水面细节”选项同时影响 CPU 与 GPU 性能；GamersNexus 在 Xbox One X 上偶尔观察到一条清晰的分界线，线外不再渲染波浪，PC 上这一距离远到看不见 [11]。这说明海面位移存在按距离分级的截断。可供对照的公开数字是《Atlas》的 GPU 风浪模拟约 0.5 ms [13]。按本报告推荐的结构估算各部分开销估算：

8.2 网络带宽

海面本身几乎不占带宽：海况参数只在变化时发送，时钟同步每秒几次往返，合计每秒几十到一百多字节。主要流量来自船体快照。按 Fiedler 的压缩方法，四元数用“最小三分量”编码只需 29 位 [48]；本报告估算一艘船一次快照约 23 到 35 字节估算：

8.3 能否用于手游

结论：可以，但要分档降级。同步结构（共享时钟、服务器权威、相对基座）与平台无关，移动网络抖动更大，反而更需要较长的插值缓冲和竖直重建。主要压力在渲染：

  • FFT 的带宽成本。256² 的复数 FFT 用 fp32 存储约 512 KB；若每个蝶形阶段都读写整张图，单帧约 32 MB 的显存流量，在移动端偏贵。改为在线程组共享内存中完成一整行或一整列、只做两次调度，可降到约 4 MB；再用 fp16 存储减半估算。中高端机上 1 级 256² 或 2 级 128² 可行。
  • 半精度的相位问题。相位 ω·t 随时间无界增长，fp16 很快失去精度。采用 Tessendorf 的量化色散后，所有分量以周期 T 循环，只需传入 t mod T，相位天然有界，同时解决了循环与精度两个问题 [7]。
  • 烘焙替代。《刺客信条 III》在主机上就使用了预计算、可循环的位移纹理 [31]。手游可以离线生成周期为 T 的位移序列，例如 64 帧 × 256² × RGBA8 约 16 MB，压缩后数 MB；CPU 与服务器读同一份数据，浮力天然一致。
  • 最低档。《战舰世界》为兼顾低端硬件放弃 FFT，改用 3 张静态高度图叠加 [37]；Unity 面向移动端的 Boat Attack 在顶点着色器中用半精度计算最多 10 个 Gerstner 波，CPU 用同一公式供浮力使用 [41]。腾讯的 Aqua 方案也指出移动端对计算着色器的支持仍有困难，降级时回退到 CPU 驱动的 LOD 选择与烘焙贴图 [45]。

适用游戏类型与收益

FFT 海面、浮力与共享时钟同步分别适合哪些游戏，哪些游戏应选择烘焙或美术定义的海浪

本报告还原的技术由三层组成：FFT 频谱海面与海况分档（第 2 章）、浮力探针与可在 CPU 上求值的玩法波段（第 3 章）、共享时钟上的确定性海面与服务器权威的船体（第 4 章）。三层可以分开采用。第一层的收益是大面积、可调海况的海面，第二层的收益是船与浪的运动吻合，第三层的收益是多人之间看到同一片浪，且海面本身几乎不占带宽（第 8.2 节）。游戏需要的层数越多，这套方案相对其他做法的优势越明显。

适用的游戏类型

游戏类型海面在玩法中的作用需要的层主要收益参考案例

不适合的类型

  • 以近岸碎浪或单个巨浪为视觉焦点的游戏。FFT 海面是空间均匀、周期重复的随机波场，无法指定某一道浪在何处、以何种形状破碎。《地平线：西之绝境》使用烘焙的碎浪截面加美术绘制的波前曲线[39]，《神秘海域》使用以单个参数控制峰形的波粒子[46]。
  • 线性关卡与过场为主的游戏。镜头与航线都是设计好的，循环播放的离线海洋模拟更便宜、美术控制更强，《使命召唤：二战》即采用这一做法[40]；共享时钟与服务器权威在这类游戏中没有用处。
  • 以河流、湖泊等内陆水体为主的游戏。FFT 依赖深水色散关系与大尺度风浪频谱，对窄水面、浅水与水流没有优势；UE5 Water 的 Gerstner 波与样条水体已能覆盖这类需求[35]。
  • 依赖确定性帧同步（lockstep）的多人游戏。本方案的船体由服务器权威模拟，因为浮点物理在不同平台上不能保证逐位一致[23][24]；采用帧同步的游戏需要定点数实现的海面与浮力，结构上与本方案不同推断。

建议的采用顺序

先确定游戏需要哪几层：单机游戏只做第一、二层，并让浮力读取 CPU 上的玩法波段；多人游戏从一开始就把海面写成“种子、参数、时间”的纯函数，并替换引擎默认的服务器时间（第 6.5 节），因为这两点在后期很难补救；风暴的空间权重场与船体竖直运动的客户端重建（第 6.3、6.4 节）可以在基础同步稳定之后再加入。

10.1 实施步骤

  1. 单机海面。先实现 GPU 端的频谱初始化与逐帧推进：每个级联一张 h₀(k) 纹理（启动时由种子生成），每帧一个 compute pass 写入 h̃(k,t) 与位移、导数的频域数据，再做水平、竖直两次逆 FFT。输出 RGBA16F 位移图与法线、雅可比图。级联边长建议取 500 m、85 m、17 m 量级，彼此不成整数比以减少可见的平铺。
  2. 材质与网格。用环形网格覆盖视野，材质在 WPO 中叠加各级联位移；按 SIGGRAPH 论文的描述实现深水色、次表面色混合与浪峰遮罩 [1]；泡沫由雅可比阈值生成，写入一张随时间反馈模糊的缓冲。
  3. 玩法波段。在 C++ 中实现与最长级联相同的频谱推进（同一种子、同一组参数），得到 64² 的 CPU 位移图；客户端也计算它并上传给 GPU，作为最长级联直接使用，保证画面与物理看到同一组长浪。实现带 3 到 4 次不动点迭代的 QueryHeight。
  4. 海况与风暴。FSeaState 复制到所有客户端；风暴中心写成 f(T)；在材质和 CPU 查询中按同一权重场混合平静与风暴两组振幅与 choppiness。
  5. 网络时钟。客户端每秒发送数次带本地时间戳的 Server RPC，服务器以 Client RPC 回传其时间；保留最近若干样本，取往返时间最短者计算偏移；本地时钟以不超过 1% 到 5% 的速率追赶目标偏移。替换 Water 插件或自写海面中所有读取时间的位置。
  6. 船与浮力。服务器上用 Chaos 刚体加浮力探针（或平面拟合）模拟船；舵与帆输入经 Server RPC 进入；先用引擎的物理复制（Predictive Interpolation 模式 [50]）跑通，再实现自定义快照与“水平插值加竖直重建”。
  7. 甲板角色。角色以船为基座移动，检查在纵摇与横摇时客户端是否滑动、抖动；必要时改为在船的局部坐标系中存储与复制位置，客户端先插值船，再合成角色。
  8. 教学化表现。见下方开关清单。用编辑器的网络模拟（Network Emulation）设置延迟与丢包，在 PIE 中以一个监听服务器加两个客户端运行。

10.2 用于展示原理的开关与可视化

  • 海面分层显示：单独显示涌浪级联、各画面级联与合成结果；调节风速时实时显示谱峰波长与有效浪高。
  • 浮力探针可视化：探针位置、查询到的海面点、受力箭头；切换探针数量、切换“直接求值 / 反解位移”。
  • 时钟开关：关闭网络时钟后各客户端退回本地时钟，海面立刻错相；屏幕角落显示当前偏移估计与往返时间。
  • 船的呈现方式切换：整体插值、海面回退、水平插值加竖直重建；显示服务器真值的半透明轮廓。
  • 风暴权重场的俯视叠加图，以及当前船位置的海况权重。

10.3 注意事项

  • 专用服务器没有渲染线程上的 GPU 资源，所有判定只能使用 GTLOceanCPU；不要在服务器代码路径中读取渲染目标。
  • 材质参数集合只接受单精度标量，时间必须先取模再写入，否则长时间运行后海面会出现阶跃。
  • FRepMovement 的旋转量化分 8 位与 16 位分量两档 [51]。8 位分量的角度分辨率约 1.4°，船长数十米时船艏会出现半米以上的位置误差，船应改用 16 位分量或自定义四元数压缩。
  • Chaos 物理子步与浮力探针的阻尼要一起调，低帧率服务器上纯刚体浮力容易振荡，这也是《Atlas》改用平面拟合的原因 [13]。
  • UE Water 插件可用于快速原型（Gerstner 波与浮力组件 [36]），但它不是 FFT 海面，复现《盗贼之海》的外观需要自写 GPU 级联。

Unity 复现对照

供其他引擎的读者参考
  • 海面：Crest（开源，URP/HDRP/内置管线）提供 FFT 波与以相机为中心的 LOD；HDRP 的 Water System 也提供频谱波段与脚本侧的水面查询。自写时用 Compute Shader 实现频谱推进与逆 FFT。
  • 时钟：Crest 的 TimeProviderNetworked 只需设置相对服务器的时间偏移 [16]；偏移本身可取自网络库的服务器时间（如 Netcode for GameObjects 或 Mirror 的网络时间）。
  • 浮力与查询：Crest 默认的 GPU 查询是异步的，需要逐帧轮询直到结果返回；无 GPU 的服务器可以使用烘焙的 FFT 数据走 CPU 路径，但有功能限制 [44]。
  • 船的同步：Netcode for GameObjects 的网络刚体与插值，或 Netcode for Entities 的预测；同样需要处理船与海面的时间线对齐。
  • 主要差异：Unity 侧有现成的联网时间接口与开源 FFT 海洋，搭建更快；UE 侧需要自写 FFT 级联与网络时钟，但 Chaos 网络物理提供了三种现成的复制模式。

结论

  1. 巨浪：《盗贼之海》的海面是 Tessendorf FFT 海洋，分平静、普通、风暴三档 [1]。由 Phillips 谱可推出浪高与风速平方成正比，少量参数即可得到量级不同的海面；风暴的局部性、浪尖的青绿透光和泡沫进一步放大了视觉上的“夸张”。风暴区的空间混合方式未公开。
  2. 船体：浮力探针或平面拟合加弹簧是游戏中的主流做法；FFT 海面的高度查询必须反解水平位移；物理用的海面应能在 CPU 上求值，因为专用服务器没有 GPU。
  3. 一致性：海面靠“共享时钟 + 确定性函数”在各端独立求值，Rare 的海浪同步表述、云层只同步偏移向量与全服一致的风暴路径都符合这一结构 [3][1][8]；船由服务器权威模拟并复制，舵轮等输入经服务器转发 [2]；甲板玩家使用相对船体的坐标。
  4. 改进方向：明确划分玩法波段与画面波段；单独控制涌浪振幅；用确定性的空间权重场表现风暴；客户端按本地海面重建船的竖直运动，消除快照插值带来的时间线错位；用 NTP 式单调时钟替代引擎默认的服务器时间。
  5. 复现与移植：UE5 中需要自写 GPU FFT 级联与网络时钟，浮力与复制可以借助 Chaos；手游可按 FFT、烘焙序列、顶点 Gerstner 三档降级，同步结构无需改变。
